# I2.3 — Database resilience checklist (manual)

Manual verification of the retrying DB connection (`DatabaseRetryPolicy`: EF Core
`EnableRetryOnFailure`, 6 retries, 6 s maximum delay) and the Azure SSL startup rule, against the
local Docker Postgres. Run the scenarios in order. Each one says whether **failure is the expected
outcome**.

## Before you start

- Branch with I2.3 checked out, `dotnet build ./backend/SatelliteTracker.sln` passes.
- `.env` exists next to `docker-compose.yml` (see CLAUDE.md, "Local secrets").
- The local connection string in user-secrets uses the recommended parameters (placeholders, put
  your own password in):

  ```bash
  dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=localhost;Port=5435;Database=satellite_tracker;Username=satellite_user;Password=<your-local-password>;SSL Mode=Disable;Timeout=15;Command Timeout=30;Keepalive=30;Maximum Pool Size=20" --project backend/src/SatelliteTracker.API
  ```

- Every other required setting is set (`dotnet user-secrets list --project backend/src/SatelliteTracker.API`
  shows `N2YO:ApiKey`, `Admin:ApiKey`, `Firebase:ServiceAccountJson`).
- Run all commands from the repository root. Two terminals: **T1** runs the API, **T2** runs
  Docker, `psql` and `curl`. Git Bash commands are shown. Where a PowerShell form differs, it is
  given too.
- The API listens on `http://localhost:5076` (launch profile `http`). Start it so the log is also
  saved to a file you can search afterwards:

  ```bash
  # T1 (Git Bash)
  dotnet run --project backend/src/SatelliteTracker.API --launch-profile http 2>&1 | tee api.log
  ```

  ```powershell
  # T1 (PowerShell)
  dotnet run --project backend/src/SatelliteTracker.API --launch-profile http 2>&1 | Tee-Object api.log
  ```

  `api.log` is local scratch. Don't commit it (delete it when done).

- `psql` shortcut used below (runs inside the container over the local socket, no password):

  ```bash
  docker compose exec postgres psql -U satellite_user -d satellite_tracker
  ```

### Job schedule (needed to read the results)

| Job | First run | Then | After a failed run, the next attempt is |
|-----|-----------|------|------------------------------------------|
| `TleUpdateJob` | at startup | every 2 h | 2 h later |
| `PassCalculationJob` | at startup | every 1 h | 1 h later |
| `PassNotificationJob` | at startup | every 60 s | 60 s later |
| `PassRetentionJob` | at startup | daily 03:00 Asia/Jerusalem | next 03:00 |

Jobs don't re-run early after a failure. Only `PassNotificationJob` shows recovery within
minutes. For the others, "recovers on the next tick" means the next scheduled run, or a restart
of the API (each job runs once at startup).

### Log lines to know

| Meaning | Text to search for (category) |
|---------|-------------------------------|
| EF is retrying a transient fault | `A transient exception occurred during execution. The operation will be retried after` (`Microsoft.EntityFrameworkCore.Infrastructure`) |
| Retries exhausted | `The maximum number of retries (6) was exceeded` |
| Per-attempt noise during an outage (expected) | `An error occurred using the connection to database` / `Failed executing DbCommand` (`Microsoft.EntityFrameworkCore.Database.*`) |
| Pass calculation OK | `Upserted passes for satellite` and `Calculated passes for` |
| Pass calculation failed | `Failed to fetch active satellites` / `Pass calculation failed for` |
| TLE update OK | `Received HTTP response 200` for the N2YO `tle` URL (`apiKey=REDACTED`) |
| TLE update failed | `Failed to retrieve active satellites` / `Failed to fetch TLE for NORAD` |
| Notification tick OK | no warning, or `No active testers with an FCM token configured` if no tester has a token |
| Notification tick failed | `Failed to get user settings` (or another `Failed to get ...`) |
| Retention OK / failed | `Pass retention deleted` / `Pass retention failed` |
| **Must never appear** | `Unhandled exception`, `BackgroundService failed`, `Hosting failed to start`, the process exiting |

Never paste the full log anywhere public. Exception messages can contain the host and port.

### Duplicate check SQL (used in several scenarios)

Both must return **zero rows**. (The unique indexes `IX_Passes_SatelliteId_OrbitNumber` and
`IX_PassNotificationLogs_PassId_ApiKeyId_AlertMinutes` should make this impossible. The query
checks that they did their job.)

```sql
-- Passes: one row per (satellite, orbit)
SELECT "SatelliteId", "OrbitNumber", count(*)
FROM "Passes"
GROUP BY "SatelliteId", "OrbitNumber"
HAVING count(*) > 1;

-- Notification log: one row per (pass, tester, threshold)
SELECT "PassId", "ApiKeyId", "AlertMinutes", count(*)
FROM "PassNotificationLogs"
GROUP BY "PassId", "ApiKeyId", "AlertMinutes"
HAVING count(*) > 1;
```

Also useful, to compare before/after:

```sql
SELECT s."Name", count(*) FILTER (WHERE p."Aos" >= now()) AS upcoming, count(*) AS total
FROM "Passes" p JOIN "Satellites" s ON s."Id" = p."SatelliteId"
GROUP BY s."Name";

SELECT "Status", count(*) FROM "PassNotificationLogs" GROUP BY "Status";
```


Expected:
- `GET /api/satellites` → `200` in well under a second.
- In the log: `Upserted passes` + `Calculated passes for` per active satellite (EROS C3,
  RUNNER 1); an N2YO `tle` response 200 per satellite; `Pass retention deleted N passes`; no
  notification `Failed to get ...` warnings.
- No retry lines. Duplicate check: zero rows.

- [ ] Baseline passes: every job logged a successful cycle, no retries, no duplicates.

## 2. Short outage — `docker compose restart postgres` while the app runs

**Expected outcome: success. Retries absorb the outage, nothing fails, nothing is duplicated.**

Setup: scenario 1 state (API running, Postgres up). Have the duplicate check open in `psql`.

```bash
# T2: keep requests flowing so something hits the restart window
for i in $(seq 1 40); do curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://localhost:5076/api/satellites; sleep 1; done &
docker compose restart postgres
wait
```

To make the **pass upsert** hit the restart too (its only automatic run is at startup or hourly):
stop the API (Ctrl+C in T1), start it again and, **as soon as** `Now listening on` appears, run
`docker compose restart postgres` in T2. Repeat once or twice if the log shows the calculation
finished before the restart.

Then wait at least 60 s, so one more notification tick runs, and check:

```bash
grep -n "transient exception occurred" api.log | tail
grep -nEi "maximum number of retries|unhandled exception|BackgroundService failed" api.log   # expect nothing new
```

Run the duplicate check SQL and the counts query.

Expected:
- One or more `A transient exception occurred ... will be retried after Nms` lines around the
  restart (typically `57P01 terminating connection due to administrator command`, or a
  connection refused while Postgres comes back).
- Every `curl` line is `200`. Some take a few seconds longer during the restart.
- No `maximum number of retries`, no unhandled exception. The process is still running.
- The next notification tick runs normally. If the upsert ran during the restart, it still ends
  with `Upserted passes ...` and the upcoming count matches scenario 1 (±passes that have since
  started).
- Duplicate check: **zero rows** in both queries.

- [ ] Short outage absorbed: retries in the log, all requests 200, process alive, no duplicate passes or notification-log rows.

## 3. Long outage — `docker compose stop postgres` for about 60 s

**Expected outcome: failure during the outage (clean, logged, process stays up), then recovery.**

Setup: API running, Postgres up.

```bash
# T2
docker compose stop postgres
date                                    # note the time
# wait ~60 s; meanwhile:
curl -s -w "\n%{http_code} %{time_total}s\n" http://localhost:5076/api/satellites
tasklist | grep -i SatelliteTracker     # PowerShell: Get-Process SatelliteTracker.API
docker compose start postgres
date
```

Wait at least 2 minutes after `start`, then:

```bash
grep -nE "maximum number of retries|Failed to get user settings|Failed to fetch active satellites|Failed to retrieve active satellites" api.log | tail
grep -nEi "unhandled exception|BackgroundService failed|Application is shutting down" api.log   # expect nothing
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://localhost:5076/api/satellites
```

Expected:
- During the outage: retry lines, then `The maximum number of retries (6) was exceeded`, logged
  through a job's warning (`Failed to get user settings: ...` from the notification job, once
  per tick). No unhandled exception, no shutdown. The API process is still listed.
- The `curl` during the outage returns `500` after roughly 25 s (scenario 4 measures this
  properly).
- After `docker compose start postgres`: within about 60–90 s, a notification tick runs without
  a `Failed to get ...` warning. `GET /api/satellites` → `200` and fast again.
- `PassCalculationJob`/`TleUpdateJob` only failed if their run fell inside the outage. They then
  recover at their next scheduled run (1 h / 2 h) or on an API restart. Restart the API to confirm
  `Upserted passes` appears again.
- Duplicate check SQL: zero rows.

- [ ] Long outage: failures were clean and logged, the process stayed alive, the jobs and API recovered after Postgres came back.

## 4. API during an outage — time to error and response body

**Expected outcome: failure (HTTP 500). Measure the time and record the body.**

Setup: API running, Postgres up. `GET /api/satellites` is anonymous and reads the DB on every
request.

```bash
# T2
docker compose stop postgres
curl -s -w "\nHTTP %{http_code}  total %{time_total}s\n" http://localhost:5076/api/satellites
curl -s -w "\nHTTP %{http_code}  total %{time_total}s\n" http://localhost:5076/api/satellites   # second sample
docker compose start postgres
```

```powershell
# PowerShell alternative for the timing
Measure-Command { try { Invoke-WebRequest http://localhost:5076/api/satellites -UseBasicParsing } catch { $_.ErrorDetails.Message } }
```

What to expect, and why:
- The retry delays are fixed by the policy: about 0 + 1 + 3 + 6 + 6 + 6 ≈ **22 s** of backoff (EF
  exponential backoff, capped at 6 s, ±10% jitter on the uncapped ones). The log shows each one
  as `will be retried after Nms`. Add them up to check.
- On top of that come 7 connection attempts. If each is refused at once, the total is **about
  22–25 s**. On Windows a refused connection to `localhost` can take about 2 s per attempt (TCP
  retries the SYN, and `localhost` may resolve to both `::1` and `127.0.0.1`), which can push the
  total to **35–50 s**. If you see that, repeat with the connection string's `Host=127.0.0.1` to
  tell the two apart, and note both figures.
- Status `500`. What the API returns today (record the exact body):
  `{"error":"The maximum number of retries (6) was exceeded while executing database operations with 'NpgsqlRetryingExecutionStrategy'. See the inner exception for the most recent failure."}`
  That's the exception message, passed through `BaseController.ToError` the same way as before
  I2.3. Before I2.3 the message was Npgsql's own (for example `Failed to connect to
  127.0.0.1:5435`). The body must not contain a stack trace, the password, or the connection
  string.

Record:

| Sample | Total time | Status | Body |
|--------|-----------|--------|------|
| 1 | | | |
| 2 | | | |

- [ ] API during outage: 500 after the time recorded above. The body is only the `{"error": ...}` message: no stack trace, password or connection string.

## 5. Start with the DB down

**Expected outcome: the app starts. DB work fails during the outage, then recovers.**

Setup: API stopped.

```bash
# T2
docker compose stop postgres
# T1: start the API (see "Before you start")
```

Check:

```bash
grep -n "Now listening on" api.log                      # appears within seconds
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://localhost:5076/swagger/index.html   # 200 (Development), no DB needed
grep -nE "maximum number of retries|Failed to fetch active satellites|Failed to retrieve active satellites|Pass retention failed|Failed to get user settings" api.log
```

Then bring Postgres back and wait at least 90 s:

```bash
docker compose start postgres
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://localhost:5076/api/satellites
```

Expected:
- `Now listening on http://localhost:5076` appears straight away, not after the retries. Startup
  never connects to the DB. `Firebase initialized` is logged.
- About 25 s later, each startup job logs its failure: `Failed to fetch active satellites`
  (pass calculation), `Failed to retrieve active satellites` (TLE), `Pass retention failed`,
  `Failed to get user settings` (notification). No unhandled exception, no exit.
- After `start`: the next notification tick succeeds and `GET /api/satellites` → `200`. Pass
  calculation, TLE update and retention next run on their schedule (1 h / 2 h / 03:00). This
  scenario passes once the notification job and the API have recovered. Restart the API to see the
  other three succeed.

- [ ] Start with DB down: the API started and served non-DB requests, jobs logged clean failures, and recovered after Postgres started.

## 6. SSL rule — Azure host without `VerifyFull`

**Expected outcome: failure. The API refuses to start. No DB needed.**

The environment variable overrides user-secrets for this run only. Your stored secret is not
changed. The host is a made-up placeholder.

```bash
# T1 (Git Bash)
ConnectionStrings__DefaultConnection="Host=example-server.postgres.database.azure.com;Port=5432;Database=satellite_tracker;Username=satellite_user;Password=placeholder;SSL Mode=Disable" \
  dotnet run --project backend/src/SatelliteTracker.API --launch-profile http
```

```powershell
# T1 (PowerShell)
$env:ConnectionStrings__DefaultConnection = "Host=example-server.postgres.database.azure.com;Port=5432;Database=satellite_tracker;Username=satellite_user;Password=placeholder;SSL Mode=Disable"
dotnet run --project backend/src/SatelliteTracker.API --launch-profile http
Remove-Item Env:ConnectionStrings__DefaultConnection
```

Repeat with `SSL Mode=Require`, and with the `SSL Mode=...` part removed. Both must fail the same
way. Then run it once with `SSL Mode=VerifyFull`: the host **starts** (`Now listening on`), and
the jobs then fail to connect to the made-up host, which is expected. Stop it with Ctrl+C.

Expected for `Disable` / `Require` / missing:
- The process exits before `Now listening on`, with an `OptionsValidationException` containing:
  `ConnectionStrings:DefaultConnection must set SSL Mode=VerifyFull when Host is an Azure Database for PostgreSQL server (.postgres.database.azure.com).`
- The message does **not** contain `example-server`, `placeholder`, or the connection string.

- [ ] SSL rule: Disable / Require / missing refuse to start with the rule named and no value echoed. VerifyFull starts.

## 7. Pool ceiling — at most 20 connections

**Expected outcome: success. The app's connection count stays ≤ 20 under load.**

Setup: API running, Postgres up (scenario 1 state).

```sql
-- in psql: the API's connections (excludes this psql session). Run with \watch 1
SELECT count(*) AS app_connections,
       count(*) FILTER (WHERE state = 'active') AS active,
       count(*) FILTER (WHERE state = 'idle')   AS idle
FROM pg_stat_activity
WHERE datname = 'satellite_tracker'
  AND usename = 'satellite_user'
  AND backend_type = 'client backend'
  AND pid <> pg_backend_pid();
\watch 1
```

In T2, generate concurrent load (50 parallel requests, 1,000 total):

```bash
seq 1000 | xargs -P 50 -I{} curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5076/api/satellites | sort | uniq -c
```

Expected:
- At rest: a handful of idle connections.
- Under load: `app_connections` climbs but **never exceeds 20**. Requests beyond the pool wait
  for a free connection instead of opening more. The `uniq -c` output is all `200`. If a request
  ever waits longer than `Timeout=15` for a pooled connection, it fails with "The connection
  pool has been exhausted". Record it if that happens.
- After the load: idle connections are pruned back over the next few minutes (Npgsql's idle
  lifetime is 300 s by default).

Record the peak `app_connections`: ____

- [ ] Pool ceiling: the peak app connection count was ≤ 20, every request returned 200.
